What changed (each measured on its own, text L4 / style L4 native unless noted)
- run() split into run() + runChunk(i0, i1), 16 KB per call, state between calls in the arena and a
  few globals. Native: no change. wasm fresh process: 15.2 -> 8.8 s / 4.4 -> 2.7 s, i.e. the
  optimizing tier is now used (within 2% of --no-liftoff). Chunk size 2 KB .. 64 KB: no difference.
- Table pointers (RECIP, STRETCH) copied to locals; counter / history update passes compute into the
  local arrays and store in separate loops (as c/fm4.c does), so they vectorize: 3.90 -> 3.65 / no change.
- Mixer kernels dot16 / upd16 as @[unchecked] functions over fixed blocks of 16 and 8 inputs (count
  rounded up to 8, padding inputs are 0): 3.65 -> 2.83 / 1.33 -> 1.10. The plain-loop form is kept
  for wasm32 (blocks are 10% slower there without SIMD), selected by the constant sizeof(*u8).
- Arena on a 64-byte boundary (one hash bucket = one cache line) and, in the native CLI, on 2 MB
  huge pages (posix_memalign + madvise, what c/fm4.c big_alloc does): 2.83 -> 2.61 / 1.10 -> 0.97.
  This was the main reason text was further behind C than images: text uses ~20 tables of 16-32 MB.
- Hash-table fill in an @[unchecked] helper so that it vectorizes (up to 640 MB at L5):
  2.61 -> 2.49, text L5 4.31 -> 4.15.
Tried and not kept
- @[unchecked] on runChunk: text L1 -4%, L4 -3%, L5 -5.5%, images 0 .. -2% (no longer a regression
  on images, which came from the mixer loops falling into the scalar remainder at 23 inputs). Not a
  clear gain, and runChunk decodes untrusted input: checks kept.
- Splitting the bucket read / stretch loops as well: slower (3.67 -> 3.85).
- A never-true "nctx > 32 -> return" guard to let LLVM drop index checks: no effect.
- dot16 with 8 explicit partial sums: scalar code, worse. upd16 without the temporary array (also
  with @[always_inline]): scalar code, 4.2 s.
- --clang-flag -msimd128 for wasm: no effect (see Makefile, wasm4simd).

What changed
- make wasm4 builds with --clang-flag -msimd128; wasm4simd / fm4.simd.wasm are gone. Same source,
  -msimd128 vs --cpu bleeding-edge: 5.29 vs 5.22 text, 2.02 vs 2.03 style, i.e. the same.
- dot16 / upd16: the block form on every target (the sizeof(*u8) switch and the plain loops are gone).
  With simd128 the blocks are faster in wasm too: style 2.02 -> 1.88, text 5.29 -> 5.24.
- upd16 takes @[noalias] w, st and stores directly; the temporary array is gone. Speed unchanged
  (native and wasm). @[noalias] alone, with the array kept, gives the same native binary bit for bit.
Tried and not kept
- @[noalias] on dot16: it only reads, nothing to gain. On olsUpd (o, Lm, cnt): audio 1.68 vs 1.65,
  video 3.17 vs 3.22, no gain.
- Dropping the local copies of RECIP / STRETCH in runChunk: 0 .. 2% slower (text L4 2.51 vs 2.42,
  L5 4.23 vs 4.17, wasm text 5.23 vs 5.14). The automatic copy does not apply, the loop makes calls.
- __TARGET_WASM__: not needed, no target switch is left.

== 2026-11-18: profile and speed-up (i7-6700, level 4, user seconds, min of 3) ==
Profile of the C build, text 1 MB (serialized rdtsc sections, about 1100 cycles per bit in total, 21 contexts):
  bucket lookup (memory) ~20%, counter load + stretch + history map ~15%, mixer dot products ~15%,
  counter + history-map update ~14%, mixer weight updates ~10%, APM ~10%, byte-level setup ~9%, coder + rest ~7%.
  No single hot spot after the changes below; cost is about 50 cycles per context per bit.
Changes (output byte-identical):
  C: mixer kernels in fixed blocks of 16 (inputs past the real count are 0), each dot product computed once,
     second nibble's buckets prefetched one bit earlier, 16-bit stretch table, built with clang.
  C + BPL: least-squares solve column by column (same subtraction order per element, vectorizable).
                          C before (gcc)   C now (clang)   BPL before   BPL now
  text 1 MB (ts)               3.42            2.56           2.58        2.60
  image 640x426                2.17            1.52           1.63        1.58
  audio mono 0.96 MB           2.61            1.96           2.33        2.04
  video 2 frames 640x360       3.51            2.72           3.14        3.05
Tried, no gain in BPL: earlier prefetch, 16-bit stretch table (both within noise, not kept).

== 2026-11-18: BPL vs C gap (i7-6700, level 4, user s, min of 3-4, pinned to one core) ==
Found with a ptrace sampling profiler (per source line) and microbenchmarks:
  1. runChunk was not @[unchecked]: bounds checks in the image/video code. Marking it unchecked: video 3.21 -> 2.97.
  2. int loop indexes: BPL int +,-,* wrap (R-TYPE-13) and are emitted without nsw, so LLVM keeps a sext per
     index and cannot widen the induction variable. 16-input OLS microbenchmark: int indexes 1.52 s, long 1.22 s,
     C 1.25 s. olsUpd now uses long indexes. Reported to bpl3 (opt-in nsw attribute requested).
